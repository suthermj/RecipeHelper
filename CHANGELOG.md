# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).
This project is deployed continuously (no version tags), so entries are grouped
by date rather than by release version.

## [Unreleased]

### Added

- Kroger cart preview (`Cart/PreviewAddToCart`) now groups items into three collapsible sections instead of one flat list: "Needs review" (a conversion fallback/guess was made — starts expanded), "Correctly mapped" (converted cleanly — starts collapsed), and "Not mapped" (couldn't be converted at all, see below — starts expanded). Unchecking a row now collapses it to just the checkbox, a small image, and the name, greyed out, instead of continuing to show its full price/notes/quantity detail — keeps a long list of excluded items from eating vertical space.

- Meal plan day picker now offers "Add '<typed text>' as a placeholder" when nothing you've imported matches what you typed, so a day can hold a plain-text reminder (e.g. "homemade pizzas") instead of requiring an already-imported recipe. `MealPlanEntry.RecipeId`/`Recipe` are now nullable and a new `FreeText` column holds the label; free-text entries render with a pencil icon and italic name, aren't included in ingredient aggregation (`SubmitDinnerSelections`), and can be removed the same way as a recipe entry. (#70)
- Recipe images now upload with a long-lived, immutable `Cache-Control` header (`public, max-age=31536000, immutable`, same value already used for fingerprinted static assets), so repeat page loads serve them from the browser's HTTP cache instead of re-fetching from Blob Storage every time. Existing images were one-time backfilled with this header directly against production (backfill script has since been removed — it isn't needed again since every new upload sets it automatically). (#54)
- Recipe images are also resized (max 2000px) and recompressed (JPEG quality 88) server-side on upload, mirroring the approach already used for photo-import — reduces per-image transfer size over the transatlantic Hetzner (Germany) ↔ user (US) path on first load. Existing images were similarly one-time recompressed and repointed at new, smaller blobs directly against production. (#54)
- Imported recipes now re-host their image onto our own Blob Storage at import time (`ImportService.RehostExternalImageAsync`) instead of linking the recipe source site's URL directly — gets the same resize/recompress + immutable Cache-Control as a manual upload, and stops page loads depending on some random blog's or Spoonacular's own server speed. Falls back to the source URL if the download fails (e.g. a site blocking non-browser requests) rather than leaving the recipe with no image. All 18 recipes that still pointed at an external image were one-time re-hosted the same way directly against production. (#54)
- Manual "Deploy to Production" GitHub Actions workflow (`workflow_dispatch`, runnable from the GitHub mobile app), reaching the VM over Tailscale via OIDC federated identity so no long-lived secret is stored in GitHub.
- Deploy workflow now also fires automatically on every PR open/push targeting `main` that touches source code, deploying that PR's head commit so it's live for on-device testing without a manual run. Docs-only commits (`**.md`) are skipped and don't trigger a redeploy. A newer push cancels an in-flight deploy of a now-stale commit rather than queuing behind it, and forked PRs are blocked from ever triggering a deploy with this repo's secrets.
- Service worker `CACHE_VERSION` is now auto-stamped to the deployed commit SHA by both `deploy/deploy.sh` and the GitHub Actions deploy workflow, so every deploy evicts old PWA caches automatically instead of relying on someone remembering to hand-bump the version.
- "Update available — tap to refresh" banner (`site.js`) when a new service worker finishes installing. `sw.js` no longer calls `skipWaiting()` unconditionally on install, so an already-open tab isn't silently swapped to a new version mid-session — the user chooses when to reload.
- Kroger cart preview (`Cart/PreviewAddToCart`) now shows an estimated total, computed from each item's price × quantity for only the currently checked items, and updates live as items are checked/unchecked or quantities edited — no page reload or submit required. Applies the same 10% Kroger-brand discount (brand contains "kroger", "simple truth", "private selection", or "hemisfares") already used on the shopping list view. (#49)
- A brief scale "pop" on the target day card when dragging a meal plan entry crosses into a new day, as a visual stand-in for haptic feedback — iOS Safari doesn't expose the Vibration API (or any haptics API) to web content, so this is the closest substitute available to a PWA. (#47)
- "Share this week" button on the Meal Plan page, generating a public, unguessable read-only link (`/Share/MealPlan/{token}`) showing each day's recipe name and photo (no ingredients/instructions). The link always reflects the plan's current live state. Opens the native iOS share sheet via `navigator.share`, falling back to copy-to-clipboard when unavailable. (#60)
- Photo import now extracts ingredient section headings (e.g. "Blackening Seasoning", "Tomato Parmesan Cream Sauce") instead of flattening every ingredient into one list — `RecipeIngredient.Section`/`SortOrder` already existed for manual Create/Edit recipes but photo and URL import never populated them. The vision prompt now returns a `section` per ingredient (copied verbatim from the heading it's printed under, or null for an unlabeled single list), threaded through `ImportRecipeVM` → the mapping page → `RecipeIngredient` on save. The import photo preview and ingredient-mapping page both show the section groupings so you can confirm them before saving; ingredient merging in `ImportService.GetImportedRecipePreview` is now section-aware too, so the same ingredient name under two different headings (e.g. salt in both the base recipe and a seasoning blend) stays split instead of collapsing into one row. URL-based Spoonacular import doesn't set sections (Spoonacular doesn't reliably expose them), so those imports behave as before.
- Meal plan entry rows (`Dinner/Index`) are now tappable — tapping a recipe-backed entry navigates straight to that recipe's detail page instead of requiring a trip back through the Recipes list to search for it. Free-text entries stay non-interactive since they have no recipe to open, and the remove button and long-press drag-to-move gesture both keep working unchanged. (#76)
- Cook Mode now highlights ingredient names within each instruction step's text (`ViewRecipe.cshtml`), so they're easier to spot at a glance while stepping through a recipe one-handed at the stove. Matching is client-side, case-insensitive, tolerates simple plurals (onion/onions), and falls back to a multi-word ingredient's last word (e.g. "flour" from "all-purpose flour") when the full name doesn't appear verbatim in the step. Step text is now inserted via `innerHTML` after HTML-escaping, so highlighting can't introduce an XSS hole from imported recipe text. (#75)
- Recipe image uploads now also generate a small thumbnail derivative (`StorageService.StoreRecipeImage`, max 500px vs. the full-size image's cap) and store it on a new `Recipe.ThumbnailUri` column. Everywhere a recipe image renders as a thumbnail instead of full-size — meal plan day entries and the recipe picker (`Dinner/Index`), the recipe list (`Recipe/Recipe`), the weekly-dinner select cards (`Dinner/SelectWeeklyRecipes`), the recipe edit page's current-image preview (`Recipe/Edit`), and shared meal plan entries (`Share/MealPlan`) — now requests `ThumbnailUri` instead of the full image, cutting the transfer size for those small boxes substantially. Falls back to `ImageUri` (and generation failures fall back to no thumbnail) so nothing breaks for recipes uploaded before this existed; those pick up a thumbnail the next time their image is re-uploaded via Create/Edit or URL import. Existing recipes' thumbnails were one-time backfilled directly against production (backfill script has since been removed — it isn't needed again since every new/edited upload generates one automatically). Known gap: photo-imported recipes that use a photo as their cover image don't get a thumbnail generated at import time (the cover photo is uploaded earlier in that flow, before the thumbnail plumbing added here runs) — they fall back to the full-size image until edited. (#82)
- Full-size recipe image cap lowered from 2000px to 1400px (`StorageService.MaxImageDimension`) — the only remaining full-size context (`ViewRecipe`'s hero image) never renders wider than ~1290px even on the largest iPhone at 3x device pixel ratio, so 2000px was carrying meaningfully more bytes than any context could ever display. Existing images over the new cap were one-time re-encoded and repointed at new, smaller blobs directly against production (old oversized blobs deleted); the backfill script has since been removed the same way the thumbnail one was.

### Changed

- General efficiency pass across the meal plan, Kroger cart, recipe import, and recipe list/detail paths: `MealPlanService`'s add/move/remove-entry methods now return the already-tracked plan (loading the `Recipe` nav for a newly-added entry with a single narrow lookup instead of re-querying the whole plan graph a second time) instead of doing a full second round trip on every autosave tap; `CartController`'s "View Cart" load now batches its Kroger product-detail lookups (`KrogerService.GetProductsByUpcBatch`) instead of one sequential Kroger API call per cart line, the same fix `ConvertIngredientsToCartItems` already had; `ShoppingListController.DeleteMultiple` now deletes all selected lists in one query + one `SaveChangesAsync` instead of looping one delete per list; recipe import's ingredient canonicalization (`ImportService.GetImportedRecipePreview`/`SaveImportedRecipe`) now fans out its OpenAI calls in parallel (throttled, same pattern already used for the Kroger fuzzy-search fallback) instead of awaiting them one ingredient at a time; and the recipe list/detail/meal-plan-index/select-cards read queries (`RecipeController`, `DinnerController`) are now `async`+`.AsNoTracking()` instead of blocking, change-tracked reads.
- Loading feedback is more consistent across the app. `site.js` now exposes `showLoadingOverlay(text)` / `hideLoadingOverlay()` helpers around the shared full-screen overlay so page-level JS can reuse it instead of rolling its own indicator. `Import/ImportRecipe.cshtml` no longer declares a second, differently-styled `#loadingOverlay`/`#loadingText` (a duplicate DOM id that was silently shadowing the shared one and using stale click-to-show logic) — it now uses the same overlay as every other page. `Dinner/ReviewDinnerSelections.cshtml`'s Kroger Cart / Shopping List buttons no longer show a redundant button-text swap on top of the overlay that the form's `loading-form` class already triggers. `Dinner/SelectWeeklyRecipes.cshtml`'s submit (which had no loading feedback at all) and the "nearby store detected" switch-store flow on `ShoppingList/ViewList.cshtml` (previously a bare button-text swap) both now use the shared overlay too. (#79)
- Photo import's recipe extraction (`IngredientsService.ExtractRecipeFromNormalizedPhotosAsync`) now uses `gpt-5.4` instead of `gpt-4o` for the vision call, aiming for more accurate ingredient/quantity extraction from recipe photos.
- Logging coverage was very uneven — heavy in the recently-touched photo-import path, effectively silent everywhere else (`KrogerAuthService`, `MealPlanService`, `ShoppingListService`, `DinnerController`, `CartController`, `AuthController`'s Kroger OAuth callback, `ShoppingListController`, `ProductController`, `SettingsController`, and the URL-import fallback path in `SpoonacularService` all had zero or near-zero log calls), making Grafana of little use for anything outside that one path. Added structured `Information`/`Warning` logs at the key decision points and mutations across all of those. Also fixed several existing `LogError` calls that were dropping the actual exception (passing only `ex.Message` as a plain string instead of `ex` plus a template, losing the stack trace in Grafana) — including one in `RecipeController.DeleteRecipe` that had its arguments swapped entirely (`ex.Message` used as the format template itself, with the real message and `{id}` passed as unused positional args), so the logged line was neither the real error message nor the intended one.

### Fixed

- Kroger cart quantity conversion relied on guessing a product's density (defaulting to water when the ingredient isn't in `DensityTable`) any time the ingredient's unit didn't share a dimension with the product's size string — e.g. garlic in teaspoons against an "8 oz" jar, or broth in cups against a "32 oz" carton, where "oz" is ambiguous between fluid and weight ounces. Kroger's product-details API actually returns exact, manufacturer-reported serving data (`nutritionInformation[0].servingSize` × `servingsPerPackage`) that states the real total pack content in a cooking unit — e.g. the real "Spice World Minced Garlic 8 oz" returns `servingSize: 1 tsp` × `servingsPerPackage: 45` (the jar holds 45 tsp), and a "Kroger® 99% Fat Free Chicken Broth" carton returns `240 ml` × `4` (960 ml total) — but only the serving unit's *name* was ever captured (into an otherwise-unused field), never the quantity or serving count. `KrogerPackInfo.BuildPackInfo` now prefers this serving data over parsing the free-text size string whenever it's present and in a recognized unit, converting via a direct same-dimension division instead of a density guess — no `ConversionNote` at all when it applies, so these items now land in "Correctly mapped" instead of "Needs review" on the cart preview. Falls back to the existing size-string parsing when a product has no serving data.
- Kroger cart preview massively over-ordered for any ingredient that fell through to the "could not determine conversion" fallback (a Volume/Weight ingredient against a Unit-dimension or unparseable-size product) — reported live as "Sleeved Celery" (a "1 ct" product) needed for "1.5 Cups" showing Qty 72, and "Green Onions" needed for "10 Tablespoons" showing Qty 30. This was a regression from the same-UPC-merging fix above: that fix started summing an ingredient's amount into base units (teaspoons/grams) before calling the per-branch conversion logic, but the two fallback branches (`!pack.ParsedOk` and the final "could not determine conversion method" branch) don't do any unit-aware math — they just `Math.Ceiling` the raw quantity, assuming it's already roughly a pack count. Once that raw quantity became a base-unit amount, "1.5 Cups" became 72 base teaspoons and "10 Tablespoons" became 30, both ceiling straight through as the reported (wildly wrong) pack quantities. Both fallback branches now default to a quantity of 1 for Volume/Weight ingredients — there's no way to size a pack without a parseable size or matching dimension, so guessing 1 and flagging it for a manual check is safer than a number that looks precise but is off by 30-70x. Count-dimension ingredients (never bucketed into base units) keep using the raw quantity as before.
- Kroger cart preview over-ordered when the same product was reached by more than one differently-named ingredient row (e.g. "garlic" and "minced garlic" from different recipes both mapping to the same jar of minced garlic) — reported live as a jar showing Qty 4 for a combined need of well under one jar. `KrogerService.ConvertIngredientsToCartItems` converted each row to a pack quantity independently, so several small amounts that each individually rounded up to "1 jar" were then summed as already-rounded quantities (1+1+1+1 = 4) instead of the actual combined need being rounded up once. It now groups by UPC before converting, sums the underlying need per dimension, and rounds up a single time per product.
- Kroger cart quantity conversion had two related size-parsing bugs that could silently produce wrong order quantities with no warning shown. `KrogerPackInfo.BuildPackInfo` checked `if (parsed != null)` before trusting a parsed product size — but `KrogerSizeParser.TryParse` never returns null (it signals a failed parse via `ParsedOk` on the returned object), so that check was always true and `ParsedOk` was hardcoded to `true` regardless of whether the size string ("Varies", "N/A", "1 lb 4 oz") actually parsed. This silently disabled the existing "could not parse product size" fallback in `KrogerService.ConvertIngredientsToCartItems`, letting unparseable sizes fall through to a raw-quantity conversion (e.g. "3 cups broth" ordering 3 of whatever the product's pack count/pricing worked out to). Separately, `KrogerSizeParser` labeled every composite pack (e.g. "8 ct / 22 oz") with a generic `PackDimension.Composite` instead of its real primary dimension, and `KrogerService.AreSameDimension` treated `Composite` as dimensionally compatible with both volume and weight ingredients — so a cups-measured ingredient against an ounce-primary composite pack would be converted by dividing teaspoons by grams, a meaningless ratio returned with no conversion note. Composite packs now carry their actual primary dimension, and `AreSameDimension`/`BRANCH 2`'s count-pack matching were adjusted accordingly.
- Ingredients that couldn't be converted to a Kroger cart item (no product mapped, or the product lookup failed) used to vanish silently between the review page and the cart preview/shopping list — the user would see N ingredients on review and get fewer on the next screen with no indication which ones were dropped or why. `KrogerService.ConvertIngredientsToCartItems` now returns the skipped items alongside the converted ones; the Kroger cart preview shows a "Not mapped" list with each item's name and reason (see the collapsible-sections entry below), and the shopping-list-from-meal-plan path adds them as name/quantity-only rows instead of losing them outright. (Required adding a `Name` field to `CartItemVM` so the ingredient name, already posted by the review page, actually binds instead of being silently dropped by MVC model binding.)
- Adding items to the Kroger cart could report success even when Kroger rejected the request. `CartController.CompleteAddToCart` called `KrogerService.AddToCartAsync` (which returns `false` on a non-2xx response rather than throwing) but never checked the result, so the "N items were added" message and redirect always fired regardless of outcome. Now checks the result and shows an error instead.
- `AddToCartRequest`'s constructor cast the final cart quantity with `(int)item.Quantity`, which truncates rather than rounds up (e.g. 2.7 → 2). Every current conversion path already produces whole numbers via `Math.Ceiling`, so this was a latent under-order risk rather than an observed bug; changed to `(int)Math.Ceiling(item.Quantity)` to match every other rounding point in the pipeline.
- Added a `RecipeHelper.Tests` xUnit project (none existed) covering the two size-parsing bugs and the skipped-item reporting above — each test was confirmed to fail against the pre-fix code before the fix was applied, and to pass after.
- Kroger cart preview (`Cart/PreviewAddToCart`) applied the 10% Kroger-brand discount to the "Estimated total" at the bottom of the page but never showed it on the individual item rows — each row displayed the raw regular/promo price with no indication a discount existed, making it look like the discount wasn't being applied at all even though the total was already correct. Item rows for Kroger-owned brands (kroger, simple truth, private selection, hemisfares) now show the same "-10%" badge, discounted price, and struck-through original price already used on the shopping list view, computed from the same `UnitPrice` helper that feeds the total.
- Photo import with multiple photos (e.g. 3 DNGs from an iPhone) took ~5s longer than necessary before the OpenAI vision call even started. `IngredientsService.NormalizeRecipePhotosAsync` ran each photo's DNG→JPEG conversion / oversized-image recompression one at a time in a sequential loop — a Grafana trace + logs showed 3 DNG conversions at ~1.7s each, fully serialized, for a `TotalElapsedMs=5138` normalization step. Same shape as the Kroger cart preview fix below: independent per-item work that was serialized instead of run concurrently. Validation (size/mime checks) still runs up front in order so the right file's error surfaces first, but the actual conversion work now runs via `Task.WhenAll` instead of one `await` at a time.
- Every Blob Storage upload (recipe image edits, photo-import cover photos) paid a full Entra AAD token acquisition from scratch, because `StorageService` was registered `Scoped` — its constructor builds a `ClientSecretCredential` + `BlobServiceClient`, and Azure.Identity's in-memory token cache lives on that credential instance, so a fresh instance per request meant the cache was thrown away before it could ever be reused. Registered as `Singleton` instead (all its fields are set once in the constructor and never mutated, and the underlying Azure SDK clients are documented thread-safe), so the AAD token is now actually cached and reused across requests until it expires.
- Kroger cart preview (`Cart/PreviewAddToCart`) could take ~20 seconds to load for a cart with several dozen mapped ingredients. `KrogerService.ConvertIngredientsToCartItems` fetched each ingredient's Kroger product details one at a time in a sequential `foreach`/`await` loop — a Grafana trace of a 19.6s request showed 34 back-to-back product lookups at ~500-700ms each with zero concurrency, all successful (no retries or errors involved). It now batch-fetches all UPCs up front via the existing `GetProductsByUpcBatch` (already used elsewhere, concurrent with a 5-at-a-time throttle) and looks products up from that dictionary inside the loop instead.
- Photo import's picker preview strip showed a generic gray "DNG" tile instead of an actual thumbnail for every DNG photo, even though this PWA is iPhone-only and Safari's native image decoder can render Apple ProRAW DNGs directly. `renderPreviews` (`ImportRecipe.cshtml`) used to skip straight to the placeholder for any file it detected as DNG by name/type; it now always attempts a real `<img>` thumbnail first and only falls back to the placeholder if the browser actually fails to decode it (via a delegated `error` listener, since `<img>` error events don't bubble).
- The redirect-after-post "pending result" session keys used by `ImportController` (`ImportRecipe`, `MappedImportedRecipe`), `DinnerController.ReviewDinnerSelections`, and `CartController.PreviewAddToCart` were read but never cleared, so once a value (including a cached error) was written it kept getting replayed on every future visit to that page — not just the one reload it was meant to survive — until something else happened to overwrite the same key. In practice a failed photo import could get permanently stuck showing that same failure on every later visit to Import Recipe. Added `Utility/PendingResultCache`, a small helper the four call sites now go through: it stores a timestamp alongside the cached value and treats anything older than 10 minutes (or JSON that fails to deserialize, e.g. after a deploy changes a VM's shape) as absent and clears it, while still preserving the original reload-safety within that window. Also added a "Back to Recipes" link to Import Recipe's error state as a guaranteed way out regardless of cache state.
- Photo import (`IngredientsService.GetAllowedImageMimeType`) could reject a genuinely valid JPEG/PNG/WebP with "does not appear to be a valid JPEG, PNG, or WebP image." `Stream.Read` is allowed to return fewer bytes than requested in a single call even when more data is available, and the magic-byte check only ever issued one `Read`, so a short first read (e.g. against a disk-backed `FileBufferingReadStream` once a multipart upload spills past the in-memory threshold) could leave the 12-byte header buffer short and fail the signature check on a real image. Switched to `Stream.ReadAtLeast`, which loops internally until the buffer is full or the stream ends.
- Tapping "Update now" on the PWA update banner showed a blank screen on the ingredient review, Kroger cart preview, and recipe-import preview/mapping pages. Those pages were rendered directly from a POST (`return View(...)`, no redirect), so the browser's history entry for them was the POST itself; `site.js`'s update banner reloads via `window.location.reload()`, which resubmits that exact POST rather than just re-fetching the page, and any failure on that resubmit had nowhere good to land (see next entry). `DinnerController.SubmitDinnerSelections`, `CartController.PreviewAddToCart`, and `ImportController.GetImportedRecipePreview`/`ImportRecipeFromPhoto` now follow redirect-after-post: the computed result is stashed in session and the user is redirected to a real `[HttpGet]` action (`ReviewDinnerSelections`, `PreviewAddToCart`, `MappedImportedRecipe`, `ImportRecipe`), so these pages have a proper URL that's safe to reload. This also fixes `CartController`'s existing redirects to `Dinner/ReviewDinnerSelections` and `Views/Cart/ViewCart.cshtml`'s "Back to dinners"/"Choose dinners" links, which pointed at an action that didn't exist until now.
- `Program.cs` called `AddSession()` without ever registering an `IDistributedCache` (`AddMemoryCache()` registers the unrelated `IMemoryCache`), so any request touching `HttpContext.Session` would throw. The redirect-after-post fix above now depends on session more heavily, so added `AddDistributedMemoryCache()`.
- Any unhandled exception in production showed a blank screen instead of an error page: `Program.cs` has pointed `UseExceptionHandler("/Home/Error")` at that route since the project was scaffolded, but no `HomeController` was ever added, so the handler itself 404'd. Added `HomeController.Error` and restyled the leftover default `Views/Shared/Error.cshtml` to match the app's look.
- Editing a recipe with no existing image, uploading one, and saving showed a blank screen. `StorageService.StoreRecipeImage`'s new resize/recompress step (added above) ran outside the method's `try/catch`, so any exception during compression propagated unhandled instead of being caught like the rest of the upload path; `RecipeService.CreateRecipe`/`UpdateRecipeAsync` also dereferenced the upload result without checking for the `null` it can already return on a caught failure. The whole upload (compress + blob upload) is now one try/catch returning `null` on any failure, and both callers check for `null` and log a warning instead of crashing, leaving the recipe saved without (or with its prior) image. (#56)
- Meal plan entry rows (`.entry-row`) and their drag-ghost clone had no `user-select`/`-webkit-touch-callout` rule, so iOS's native text-selection/callout gesture competed with the long-press-then-slide move gesture in `bindMoveGestures`, making it hard to complete a drag. Added `user-select: none` / `-webkit-user-select: none` / `-webkit-touch-callout: none` to both classes. (#47)
- Import's Kroger product mapping suggestion always defaulted onion ingredients to red onion regardless of what the recipe text actually said (e.g. "yellow onion"). Both ingredient-canonicalization prompts (`IngredientsService.CanonicalizeAsync`, `TransformRawIngredients`) stripped produce color/variety as a "descriptor," so "yellow onion"/"red onion"/"white onion" all collapsed to the same canonical `"onion"` ingredient, which then carried one sticky first-mapped-wins default product. Added onion, bell pepper, potato, and apple color/variety to the prompts' "keep distinct forms" list so each color canonicalizes to its own ingredient record (and gets its own default mapping) instead of sharing one. (#77)
- Dragging a meal plan entry to a new day highlighted two different boxes at once (the whole day card, and a tighter box around just the entry rows), flickering jerkily as the drag moved. Both the day card and its inner `.day-entries` wrapper carried the same `data-day` attribute, so `closest('[data-day]')` inconsistently matched whichever was nearer depending on where the finger was. Gave the outer card its own `.day-card` class and scoped all drag-target/dim lookups to it. (#47)
- Recipe picker sheet on Meal Plan losing its header, search bar, and backdrop on reopen: `max-height: 88svh` was only ever set as an inline style, so `closePicker()`'s `pickerCard.style.maxHeight = ''` reset wiped it permanently instead of falling back to a base value. Moved the 88svh cap into the `#recipePickerCard` CSS rule (same pattern already used for the keyboard-open 72svh override) so clearing the inline override correctly restores it. (#34)
- The above picker fix wasn't reaching installed PWAs because the Meal Plan page is served via `staleWhileRevalidate` and the service worker cache version hadn't changed — fixed by the auto-stamping change above.
- Deploy workflow originally took a `ref` text input that duplicated the branch you'd already picked in the "Use workflow from" selector. Removed it entirely — the workflow now has zero inputs and just deploys `github.sha`, the commit at the tip of whichever branch was picked in that selector.
- Ingredient quantities on the recipe detail and meal plan review pages showed awkward decimals (e.g. "0.33 cup") instead of the fractions recipes are actually written in. Added `UnitConverter.ToFractionString()`, which matches the fractional part against common cooking fractions (halves, quarters, eighths, thirds, sixths) and renders "1/3", "1 1/2", etc., falling back to the old trimmed-decimal format when the value isn't close to a recognizable fraction. (#31)
- Ingredient quantity/unit text on the recipe detail view (and Cook Mode sheet) wrapped onto two lines for anything longer than ~8 characters (e.g. "1 Tablespoon", and — after the fraction-display change above — increasingly common combos like "1 1/2 Cups"), breaking row height and pushing the ingredient name out of line. The column's fixed `width: 76px` (added for issue #30 to keep names aligned to a column) was never widened to fit the longer fraction strings. Widened it to 120px, measured against realistic quantity/unit combinations, and added `white-space: nowrap` as a safety net for rare longer cases — keeps the issue #30 alignment fix intact while eliminating the wrapping. (#30)
- Photo import's "Take Photo" option could only ever hold one photo: iOS's native file picker replaces `<input type="file">`'s entire file list on every invocation (camera or library), so capturing a second shot silently wiped out the first instead of adding to it. The photo picker now tracks selections in JS state and merges each new pick into it instead of treating the picker's latest result as the whole selection.
- Photo import rejected any standard image (JPEG/PNG/WebP) over 15 MB, forcing users to compress full-resolution phone photos by hand before importing. Oversized standard images are now auto-resized (max 2000px) and recompressed (JPEG quality 88) server-side instead of being rejected — the same approach already used for DNG conversion.
- Meal plan ingredient review showed the same ingredient as separate rows (e.g. two "Minced Garlic" lines) instead of one merged entry. `SubmitDinnerSelections` aggregated by canonical `Ingredient.Id`, so two recipes' ingredients that resolve to different DB rows for the same display name (a canonicalization gap) never merged even when using the same unit. Aggregation now groups by normalized name instead, so same-unit duplicates truly merge into one line. When an ingredient genuinely has incompatible units across recipes (e.g. a bare count vs. a volume amount — there's no "cloves" measurement in this app's schema, so those import as a unitless count), it still can't be summed into one number, but its rows are now guaranteed adjacent in the list (explicit sort by section/name) instead of scattered whichever way `Dictionary` iteration happened to land.
- Creating or editing a recipe with an image upload could throw an unhandled `NullReferenceException` (blank screen in production) if the Blob Storage upload failed: `StorageService.StoreRecipeImage` already caught upload exceptions and returned `null`, but `RecipeService.CreateRecipe`/`UpdateRecipeAsync` dereferenced the result unconditionally (`blobResponse.BlobUri`). Both call sites now null-check the response, log a warning, and save the recipe without changing its image instead of crashing. (#56)
- `StorageService.StoreRecipeImage`'s catch block logged blob upload failures at `Information` level, so a genuine auth/permission failure (as opposed to the "expected" null-check case above) was invisible in Grafana instead of alerting anyone. Now logs at `Error` with the exception and blob name.
- Deploy workflow originally took a `ref` text input that duplicated the branch you'd already picked in the "Use workflow from" selector, plus the SSH key rotation, nologin-shell, and .NET repo-pinning fixes needed to get it working end-to-end (see `deploy/remote/README.md` for details).
- Kroger cart preview still showed duplicate rows for the same product when two ingredients with different names or units (e.g. "garlic" by teaspoon in one recipe, by count in another) both mapped to the same Kroger UPC — the row-merge above only dedupes by ingredient name/unit *before* Kroger mapping, so cases that only collide after mapping to the same product fell through. `KrogerService.ConvertIngredientsToCartItems` now groups its output by UPC after conversion and sums pack quantities into a single row, combining the "Needed" text and any conversion notes from each source ingredient.
